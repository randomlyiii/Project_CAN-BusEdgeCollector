> 时间段: 2026-07-28  
> 主题: 从站 CAN 中断架构修复 + 主站 OLED 多页显示 + 全链路调试

## 问题一: 从站 CAN 初始化在调度器前 → CAN 寄存器被破坏

**症状**:
```
从站 OLED 卡 "S: Starting..."，FreeRTOS 调度器正常但 CAN 通信异常
```

**根因**:
`CAN_User_Init()` 在 `main()` 中（调度器启动前）被调用。 `vTaskStartScheduler()` 内部会静默破坏 CAN 外设寄存器。已验证：调度器启动前初始化的 CAN 外设不可用。

**修复** (`main.c` + `CAN_User.c`):
```c
// ❌ 错误: main() 中调用
CAN_User_Init();
xTaskCreate(...);
vTaskStartScheduler();

// ✅ 正确: 在 CAN 任务中初始化
static void Task_CAN_Slave(void *pvParameters) {
    CAN_DeInit(CAN1);       // 先复位
    Delay_ms(10);           // 等待稳定
    CAN_User_Init();        // 重新初始化（调度器已启动，安全）
    for (;;) { /* ... */ }
}
```

**涉及文件**:
- `CanEdgeGateWay_Slave/User/main.c`
- `CanEdgeGateWay_Slave/Hardware/CAN_User.c`

**教训**: CAN 硬件初始化必须在调度器启动后的任务上下文中执行。裸机下的初始化时机在 FreeRTOS 下不适用。

## 问题二: CAN RX 中断洪泛 → 调度器被劫持 → 系统反复重启

**症状**:
```
两个从站通过 CAN 总线并联后，反复重启。
拔掉 CAN 线 → 从站正常运行。
```

**根因**:
从站使能了 CAN RX 中断 (FMP0)。在活跃的 CAN 总线上（主站 + 其他从站每秒发送数十帧），每帧触发一次 ISR。

ISR 中:
1. `xSemaphoreGiveFromISR()` 写调度器就绪列表
2. `portYIELD_FROM_ISR()` 请求 PendSV 上下文切换
3. PendSV 被执行 → 切换任务上下文
4. 高频 ISR (每秒数十次) 意味着 PendSV 几乎连续执行
5. 低优先级任务（特别是 Housekeep）被无限期饿死
6. IWDG 未及时喂狗 → **4 秒后系统复位**
7. 复位后重新使能 CAN 中断 → 死循环

**修复** (`CAN_User.c`):
```c
// 从站 CAN 架构彻底改为零中断
void CAN_User_Init(void) {
    CAN_GPIO_Init();        // PA11=IPU, PA12=AF_PP
    CAN_Init(CAN1, &can);
    CAN_FilterInit(&filter); // 全通滤波器

    // ⚠️ 无条件启用 CAN 中断 (FMP0)
    // ⚠️ 无 NVIC 配置
    // ⚠️ 无信号量创建
    // 只初始化本地缓存
    LocalCache_Init(&g_local_cache);
}
```

同时移除 `CAN1_RX0_IRQHandler` ISR 函数（`#if 0` 包围）。

**涉及文件**:
- `CanEdgeGateWay_Slave/Hardware/CAN_User.c` — 移除中断相关代码
- `CanEdgeGateWay_Slave/Hardware/CAN_User.h` — 移除 `g_can_rx_sem` extern 和 ISR 声明

**教训**: 从站仅需 TX + RX FIFO 清空。CAN 接收中断在 FreeRTOS 下是一把双刃剑——在调度器就绪后安全，但在多节点总线上频率过高会劫持调度器。纯轮询方案更适合低频采样场景。

## 问题三: RX FIFO 清空无限循环 → IWDG 饿死

**症状**:
```
修复问题二后，从站仍然间歇性重启（频率降低）。
```

**根因**:
```c
// ❌ 危险: 活跃总线上 FIFO0 可能永远不为空
while (CAN_MessagePending(CAN1, CAN_FIFO0) > 0) {
    CAN_Receive(CAN1, CAN_FIFO0, &rx_msg);
}
// → 无限循环 → Housekeep 饿死 → IWDG 复位
```

在 500kbps 总线上，主站每 10ms 发一帧（轮询 CAN Rx） + 每个从站每 500ms 发多帧。如果有 3 个节点，FIFO 接收速率可超过清空速率，导致循环永不退出。

**修复** (`main.c`):
```c
// ✅ 安全: 最多清空 16 帧/周期
CanRxMsg rx_msg;
uint8_t drain = 0;
while (CAN_MessagePending(CAN1, CAN_FIFO0) > 0 && drain < 16) {
    CAN_Receive(CAN1, CAN_FIFO0, &rx_msg);
    drain++;
}
```

**涉及文件**:
- `CanEdgeGateWay_Slave/User/main.c` — Task_CAN_Slave

**教训**: 任何基于"外部设备状态"的 while 循环必须有迭代上限。CAN 总线、UART、I2C 等外设状态寄存器不受 MCU 控制，不能假设"总会变空闲"。

## 问题四: 多从站同时上电 CAN 总线冲突

**症状**:
```
两个从站同时上电 → 偶尔一方进入 Bus-Off → CAN 通信中断
```

**根因**:
两个从站几乎同时调用 `CAN_User_Init()` → 同时开始发送 Heartbeat → CAN 总线仲裁冲突 → 错误计数累积。在极端情况下（晶振偏差 + 软件时序巧合）可能导致 Bus-Off。

**修复** (`main.c`):
```c
// 按 node_id 错峰启动: S1=0ms, S2=2000ms
vTaskDelay(pdMS_TO_TICKS((slave_node_id - 1) * 2000));
```

**涉及文件**:
- `CanEdgeGateWay_Slave/User/main.c` — Task_CAN_Slave

## 问题五: BH1750 I2C 与 OLED I2C 总线冲突

**症状**:
```
从站正常运行但 OLED 偶尔花屏/数据错乱。
```

**根因**:
BH1750 和 OLED 共用 **PB8/PB9** 软件 I2C 总线。BH1750 读操作在 **Sensor 任务 (prio 3)** 中执行，OLED 写操作在 **Housekeep 任务 (prio 0)** 中执行。

当 Sensor 任务从 Housekeep 手中抢占 CPU，而 Housekeep 正在执行 `OLED_WriteData()` 时，两个任务同时对同一组 GPIO 做软件 I2C 位操作 → 总线状态破坏。

**修复** (`sensor_manager.c` + `main.c`):
```c
// 1. 创建 I2C 互斥锁
SemaphoreHandle_t g_i2c_mutex;
g_i2c_mutex = xSemaphoreCreateMutex();

// 2. BH1750 读操作加锁
if (g_i2c_mutex) xSemaphoreTake(g_i2c_mutex, pdMS_TO_TICKS(50));
ret = BH1750_Read(&out->bh1750.lux);
if (g_i2c_mutex) xSemaphoreGive(g_i2c_mutex);

// 3. OLED 写操作加锁
if (g_i2c_mutex) xSemaphoreTake(g_i2c_mutex, pdMS_TO_TICKS(50));
OLED_UpdateDisplay();
if (g_i2c_mutex) xSemaphoreGive(g_i2c_mutex);
```

FreeRTOS 互斥锁具有**优先级继承**机制：Housekeep (prio 0) 持有锁时，Sensor (prio 3) 等待锁会自动将 Housekeep 临时提升到 prio 3，快速完成 OLED 写操作释放锁。

**涉及文件**:
- `CanEdgeGateWay_Slave/Hardware/sensor_manager.c`
- `CanEdgeGateWay_Slave/Hardware/sensor_manager.h`
- `CanEdgeGateWay_Slave/User/main.c`

## 问题六: LM393 ADC 校准/转换无限等待

**症状**:
```
从站 2 (LM393 节点) 偶尔卡在初始化阶段，不进入调度器。
```

**根因**:
`lm393.c` 中 3 处 `while()` 循环无超时保护：
```c
while (ADC_GetResetCalibrationStatus(ADC1)) { }   // 可能死等
while (ADC_GetCalibrationStatus(ADC1)) { }         // 可能死等
while (!ADC_GetFlagStatus(ADC1, ADC_FLAG_EOC)) { } // 可能死等
```

**修复** (`lm393.c`):
```c
uint32_t timeout = 100000;
while (ADC_GetResetCalibrationStatus(ADC1)) {
    if (--timeout == 0) break;
}
// 同上对另外两处 ADC 等待加超时
```

**涉及文件**:
- `CanEdgeGateWay_Slave/Hardware/lm393.c`

**教训**: 所有外设状态寄存器等待循环必须加超时。即使是"理论上一定会完成"的操作，电气噪声/晶振偏差/硬件故障都可能导致状态位永远不变。

## 问题八: 主站 OLED 格式化字符串溢出 16 字符

**症状**:
```
OLED 显示偶尔出现乱码或数据被截断。
```

**根因**:
多个 `sprintf` 格式化字符串在数值较大时输出超过 16 字符:
- Page 3 L1: `OV:%u` 中 `g_fifo_high_overflow_cnt` (uint16, 最大 65535) → **21 字符溢出**
- Page 3 L2: `RC:%u` 中 `g_bus_off_recovery_cnt` (uint16, 最大 65535) → **20 字符溢出**
- Page 1 L1: `T:%u.%uC H:%u.%u%%` 理论最大 17 字符（DHT11 实际 ≤15 字符）

**修复** (`main.c`):
1. 新增 `OLED_CompactNum()` — 将大值压缩为 `"1.2K"` / `"65K"` / `"1.2M"` 格式 (≤4 字符)
2. 所有大值 (OV/RC) 改用 `OLED_CompactNum()` 格式化
3. 传感器数值加 clamp 保护 (温度 >99 → 99, 湿度 >99 → 99, 光照 >99k → 99.9k)
4. Page 3 标签缩短: `OV:` → `O:`, `RC:` → `R:`, `ERR:` → `E:`, `FIFO:` → `F:`

**涉及文件**:
- `CanEdgeGateWay_Master/User/main.c` — 全部 4 页 OLED 构建函数

**教训**: `g_oled_line[4][17]` 每行 16 字符 + null。任何 `sprintf` 输出超 16 字符会溢出到相邻行缓冲区，破坏相邻数据。ARMCC 的 `sprintf` 无边界检查。**每个格式化字符串必须在编码时人工验证 ≤16 字符**。

## 问题十: 主站 OLED 多页显示方案实现

**需求**:
主站需要同时监视 2 个从站的状态，4×16 OLED 无法在单页显示所有信息。需要多页翻页。

**方案**:
| 页 | 名称 | 行内容 |
|----|------|--------|
| **Page 0** ★ | 仪表盘 | CAN+ETH / S1状态+心跳 / S2状态+心跳 / 告警汇总 |
| **Page 1** | 节点1详情 | DHT11温湿度 + BH1750光照 + 心跳 + 告警 |
| **Page 2** | 节点2详情 | LM393数字/模拟 + 预留通道 + 心跳 + 告警 |
| **Page 3** | 总线诊断 | 负载%+节流 / FIFO积压 / 错误级别 / RX总帧 |

**翻页行为**:
- PA0 短按: 0→1→2→3→0 循环
- 10 秒无操作: 自动回到 Page 0（仪表盘）
- 新 Alarm 到达: 强制跳到 Page 0

**涉及文件**:
- `CanEdgeGateWay_Master/User/main.c` — 4 个 `OLED_BuildPageN()` + `OLED_UpdateDisplay()` 改写
- `CanEdgeGateWay_Master/Hardware/CAN_User.h` — `SlaveNode_t` 新增 `lm393_analog/digital/reserved_ch1`
- `CanEdgeGateWay_Master/Hardware/CAN_User.c` — `CAN_ProcessFrame` 新增 `CAN_FUNC_LM393_DO` / `CAN_FUNC_RESERVED` 分支

## 问题十一: FreeRTOS 任务栈不足导致死机

**症状**:
```
从站偶发 HardFault 或 MALLOC FAILED，无特定触发条件。
```

**根因**:
最终阶段初期任务栈被缩减以节省 RAM（Sensor 256w → 阶段二已验证的 384w 不够用）。ARMCC 的 `sprintf` 单次栈消耗 150-250 字节，加上 DHT11+BH1750 驱动的调用深度，256w 栈在复杂调用链下溢出。

**修复** (`main.c`):
```c
#define STACK_SENSOR    384   // 恢复阶段二验证值
#define STACK_HOUSEKEEP 384   // 恢复阶段二验证值
```

**涉及文件**:
- `CanEdgeGateWay_Slave/User/main.c`

## 问题十三: 单节点假离线 — BusOff 期间 HeartBeatCheck 误判 + CAN_ResetBus 暴力复位

**症状**:
```
1 个从站工作时, 主站偶发假离线 (stale→OFF), 自愈慢。
2 个从站时正常。
```

**根因三合一**:

**① HeartBeatCheck 在 BusOff 期间无保护** (`CAN_User.c:494`)
```c
void CAN_HeartBeatCheck(void) {
    // ❌ 没有检查 error_level
    for (uint8_t i = 0; i < MAX_SLAVE_NODES; i++) {
        ...
    }
}
```
BusOff 时 master CAN 控制器硬件收不到任何帧, 但不代表 slave 掉线。单节点时 60Ω 终端阻抗信号完整性差 → CRC 错 → TEC↑ → BusOff → HeartBeatCheck 收不到帧 → 判 stale → 30s 后判 offline。2 节点时 40Ω 信号强不易 BusOff，所以 2 节点正常、1 节点假离线。

**② CAN_ResetBus 用 DeInit+Init 暴力复位** (`CAN_ResetBus`)
```c
void CAN_ResetBus(void) {
    CAN_DeInit(CAN1);        // ❌ 违反 CAN 协议, 软件全复位
    CAN_Hardware_Init();     // 时序/滤波器全部重配
}
```
RM0008 §25.7.4 规定: BusOff 恢复应通过 INRQ 进入/退出初始化模式, 硬件自动走 128 隐性位检测。暴力复位短时间无法重新同步总线, 且可能引发总线风暴。

**③ g_boff_consec 10ms 周期重复累加** (`CAN_ErrorMonitor`)
```c
if (error_level == 3) {
    g_boff_consec++;  // ❌ 每 10ms 加一次, 一次 BusOff 等 200ms 冷却加到 20+
}
```
导致第 2 次 BusOff 就吃 3s 冷却, 失去 200ms 快恢优势。

**修复**:

**① HeartBeatCheck 加 BusOff/Passive 保护** (`CAN_User.c:501`)
```c
void CAN_HeartBeatCheck(void) {
    /* BusOff(3)/Passive(2) 时 master 收不到帧, 不判 slave 假离线 */
    if (g_can_error.error_level >= 2)
        return;
    // ... 正常检测逻辑
}
```

**② CAN_ResetBus 改用 INRQ 协议恢复** (`CAN_User.c:255-313`)
```c
void CAN_ResetBus(void) {
    CAN1->MCR |= CAN_MCR_INRQ;            // 请求初始化模式
    while (!(CAN1->MSR & CAN_MSR_INAK));   // 等 INAK
    CAN1->MCR &= ~(uint32_t)CAN_MCR_INRQ;  // 退出初始化模式
    while (CAN1->MSR & CAN_MSR_INAK);      // 等 INAK 清除
    while (CAN1->ESR & BOFF_BIT);          // 等待 128 隐性位完成
    // 时序寄存器保持, 无需重配
}
```

**③ g_boff_consec 边沿检测** (`CAN_ErrorMonitor`)
```c
static uint8_t boff_counted = 0;

if (error_level == 3) {
    if (!boff_counted) {     // 仅跳变时累加一次
        g_boff_consec++;
        boff_counted = 1;
    }
    ...
} else {
    boff_counted = 0;        // 退出 BusOff 时清标记
}
```

**涉及文件**:
- `CanEdgeGateWay_Master/Hardware/CAN_User.c` — HeartBeatCheck + CAN_ResetBus + ErrorMonitor

**教训**:
1. BusOff 时 master 收不到帧是硬件行为, 不是 slave 的错。心跳检测必须跳过 BusOff 时段。
2. CAN BusOff 恢复不能暴力 DeInit+Init。必须用 INRQ 进入/退出初始化模式, 硬件自动走 128 隐性位。
3. 所有"周期函数内累加计数器"必须考虑调用频率。10ms 周期下 200ms 等于 20 次累加, 阈值形同虚设。

**核心经验**:
1. **从站 CAN 不需要中断**: 从站只发不收（或收后丢弃），轮询 FIFO 完全够用。中断带来的调度器干扰远超收益。
2. **所有 while 循环必须有时限**: 外设状态寄存器不受 MCU 控制，必须加超时兜底。
3. **I2C 共享总线必须互斥**: 两个不同优先级的 FreeRTOS 任务操作同一软件 I2C 总线 = 数据竞争。
4. **ARMCC sprintf 栈消耗极大**: 384 words 是调用 sprintf 的 Housekeep 任务的最低安全栈。
5. **MSP 溢出不触发 HardFault**: 它踩的是堆（ucHeap[]），表现为随机任务崩溃。MSP 至少 2KB。
6. **OLED 格式化必须在编码时验证**: `g_oled_line[17]` 无溢出检查，16 字符是硬限制。
7. **CAN 初始化必须在调度器后**: `vTaskStartScheduler()` 破坏 CAN 外设寄存器。
8. **空条件编译数组需要 Sentinel**: 所有 `#if` 条件都不满足时，C 不允许空初始化器。
9. **BusOff 时心跳检测必须跳过**: master 控制器 BusOff 时硬件收不到帧，不是 slave 掉线。加 `error_level >= 2` 保护退出。
10. **CAN BusOff 不能用 DeInit+Init 复位**: 必须用 INRQ 进入/退出初始化模式，硬件自动走 128 隐性位。违反协议可能引发总线风暴。
11. **周期函数内的计数器必须考虑调用频率**: 10ms 周期时 200ms 冷却期间加法器跑了 20 次，阈值形同虚设。加边沿检测只跳变时累加一次。
12. **FIFO 在 receive-only 模式下安全启用**: 主站不发帧则无自接收回环。双 FIFO 按优先级分流，由 ModbusTCP_SyncFromCAN 消费至历史缓存。
13. **ALARM 帧必须不计预算**: 紧急帧不受 tx_budget 限制，否则传感器掉线时 ALARM 永远发不出。
