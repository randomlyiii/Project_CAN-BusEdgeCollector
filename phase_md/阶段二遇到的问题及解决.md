## 问题一: TCB_t 缺少 ulNotifiedValue[] / ucNotifyState[] (30 errors)

**错误信息**:
```
FreeRTOS\src\tasks.c(405): error: #136: struct "tskTaskControlBlock" has no field "ulNotifiedValue"
FreeRTOS\src\tasks.c(406): error: #136: struct "tskTaskControlBlock" has no field "ucNotifyState"
... (共 30 个 error，遍布 tasks.c 405~1270 行)
```

**根因**:

`task.h` 中 TCB_t 有两个定义:
1. **顶部无守卫** (第39行): 简化版 TCB，只含 8 个字段，并设置了 `#define tskTCB_DEFINED`
2. **MPU 守卫内** (第192行): 完整 TCB，含通知/Mutex/统计字段，受 `#ifndef tskTCB_DEFINED` 保护

`tasks.c` 虽然正确定义了 `MPU_WRAPPERS_INCLUDED_FROM_API_FILE`，但顶部简化版先执行了 `#define tskTCB_DEFINED`，导致 `#ifndef tskTCB_DEFINED` 为假，完整 TCB 被跳过。通知字段 `ulNotifiedValue[]` 和 `ucNotifyState[]` 只存在于完整 TCB 中 (`configUSE_TASK_NOTIFICATIONS == 1`)，因此全部报错。

**修复** (task.h, Master + Slave):
1. 将顶部简化版 TCB + `#define tskTCB_DEFINED` 替换为前向声明: `typedef struct tskTaskControlBlock TCB_t;`
2. 移除 MPU 区域内的 `#ifndef tskTCB_DEFINED` / `#define tskTCB_DEFINED` / `#endif` 三重守卫
3. 结果: 外部代码只看到前向声明（只能声明指针），内核代码定义 MPU 宏后看到完整结构体

**涉及文件**:
- `CanEdgeGateWay_Master/FreeRTOS/inc/task.h`
- `CanEdgeGateWay_Slave/FreeRTOS/inc/task.h`

## 问题三: port.c 汇编符号未定义 (3 errors)

**错误信息**:
```
FreeRTOS\src\port.c(48): error: A1516E: Bad symbol 'pxCurrentTCB', not defined or external
FreeRTOS\src\port.c(68): error: A1516E: Bad symbol 'pxCurrentTCB', not defined or external
FreeRTOS\src\port.c(78): error: A1516E: Bad symbol 'vTaskSwitchContext', not defined or external
```

**根因**:
ARMCC v5 的 `__asm` 函数由 **armasm** 汇编器独立处理，不继承 C 级别的 `extern` 声明。即使用 C 写了 `extern TCB_t * volatile pxCurrentTCB;` 和 `extern void vTaskSwitchContext(void);`，汇编器仍然不知道这些符号。必须用 `IMPORT` 指令显式声明。

**修复** (port.c, Master + Slave):

`vPortSVCHandler` — 添加 IMPORT:
```asm
__asm void vPortSVCHandler(void)
{
    PRESERVE8
    IMPORT pxCurrentTCB          ← 新增
    ldr r3, =pxCurrentTCB
    ...
```

`xPortPendSVHandler` — 添加 IMPORT:
```asm
__asm void xPortPendSVHandler(void)
{
    PRESERVE8
    IMPORT pxCurrentTCB          ← 新增
    IMPORT vTaskSwitchContext    ← 新增
    mrs r0, psp
    ...
```

**涉及文件**:
- `CanEdgeGateWay_Master/FreeRTOS/src/port.c`
- `CanEdgeGateWay_Slave/FreeRTOS/src/port.c`

## 问题四: SysTick_Handler 重复定义 (1 error)

**错误信息**:
```
.\Objects\ceg_master.axf: Error: L6200E: Symbol SysTick_Handler multiply defined (by port.o and delay.o).
```

**根因**:
`FreeRTOSConfig.h` 中有宏 `#define xPortSysTickHandler SysTick_Handler`，把 `port.c` 的 `xPortSysTickHandler` 重命名为 `SysTick_Handler`。同时 `System/Delay.c` 也定义了 `void SysTick_Handler(void)`（作为向量表入口，桥接到 FreeRTOS）。两个 .o 都导出了 `SysTick_Handler`，链接冲突。

SVC 和 PendSV 直接用宏映射没问题（因为没有用户代码定义这些 handler），但 SysTick 的中转模式需要 Delay.c 持有向量表入口。

**修复** (FreeRTOSConfig.h, Master + Slave):
移除 `#define xPortSysTickHandler SysTick_Handler`，保留 SVC/PendSV 映射不变。

修复后的调用链:
```
向量表 → Delay.c:SysTick_Handler() → port.c:xPortSysTickHandler() → FreeRTOS tick
```

**涉及文件**:
- `CanEdgeGateWay_Master/User/FreeRTOSConfig.h`
- `CanEdgeGateWay_Slave/User/FreeRTOSConfig.h`

## 问题六: 链接时 RAM 溢出 (20 errors)

**错误信息**:
```
.\Objects\ceg_master.axf: Error: L6406E: No space in execution regions with .ANY selector matching startup_stm32f10x_md.o(STACK).
.\Objects\ceg_master.axf: Error: L6406E: No space in execution regions with .ANY selector matching tasks.o(.bss).
... (共 20 个 error)
.\Objects\ceg_master.axf: Error: L6407E: Sections of aggregate size 0xa30 bytes could not fit into .ANY selector(s).
```

**根因**:
STM32F103C8T6 总共只有 **20KB RAM**。内存占用分析:

| 项目 | 修改前 | 占比 |
|------|--------|------|
| MSP 栈 | 1KB | 5% |
| 系统堆 (libc) | 0.5KB | 2.5% |
| FreeRTOS 堆 (ucHeap[]) | **15KB** | **75%** |
| 固定占用合计 | 16.5KB | 82.5% |
| 剩余给 .data/.bss | 3.5KB | 17.5% |

实际 .data/.bss 需要 ~6.1KB (3.5KB + 溢出 2.6KB)，超过了剩余的 3.5KB。FreeRTOS 堆的 `ucHeap[]` 是静态数组，编译时计入 .bss，15KB 占掉了 75% 的 RAM。

**修复** (三处):

| 参数 | 修改前 | 修改后 | 释放 |
|------|--------|--------|------|
| `configTOTAL_HEAP_SIZE` | 15KB | **10KB** | 5KB |
| `Stack_Size` (MSP) | 1024B | **512B** | 512B |
| `Heap_Size` (libc) | 512B | **0** | 512B |
| **合计释放** | — | — | **6KB** |

其中 libc 堆归零是安全的——项目只使用 FreeRTOS 的 `pvPortMalloc`，不调用标准 `malloc()`。

**涉及文件**:
- `CanEdgeGateWay_Master/User/FreeRTOSConfig.h` (configTOTAL_HEAP_SIZE)
- `CanEdgeGateWay_Slave/User/FreeRTOSConfig.h` (configTOTAL_HEAP_SIZE)
- `CanEdgeGateWay_Master/Start/startup_stm32f10x_md.s` (Stack_Size, Heap_Size)

## 问题八: MSP 栈溢出 → 卡 "M: Starting..."（IWDG 循环复位）

**时间段**: 2026-07-24 下午（阶段二-2：恢复 W5500/CAN）

**症状**:
```
OLED 显示:
  Line 1: M: Starting...
  Line 2: FreeRTOS v10.4
  （此后无变化，约 1-2 秒后系统复位，循环）
```

**根因**:
MSP 栈（主栈，Main Stack Pointer）仅 512 字节（`0x200`）。`CAN_User_Init()` + `W5500_Init()` 的调用链深度超过 512B 时，MSP 溢出向下踩踏 `.bss` 段中的 `ucHeap[]`（FreeRTOS 堆数组），导致：
1. `pvPortMalloc()` 返回损坏的内存块
2. `xTaskCreate()` 创建的 TCB 或栈被破坏
3. 调度器启动后首个被破坏的任务运行 → 硬 fault 或死循环
4. IWDG 无法喂狗 → 1 秒后系统复位 → 重复循环

**为什么之前 3 调试任务能跑**：
调试版不调 `CAN_User_Init` 和 `W5500_Init`，MSP 调用链浅，512B 勉强够。

**修复** (`startup_stm32f10x_md.s`, Master + Slave):
```asm
Stack_Size      EQU     0x00000400    ; 512B → 1024B
```

**涉及文件**:
- `CanEdgeGateWay_Master/Start/startup_stm32f10x_md.s`
- `CanEdgeGateWay_Slave/Start/startup_stm32f10x_md.s`

**教训**:
- MSP 栈溢出是最隐蔽的故障模式之一——它踩的是 `ucHeap[]`，不是栈自身，所以不会触发 HardFault，而是表现为随机任务崩溃
- 添加重量级初始化函数（CAN_Init、SPI 外设探测）前必须评估 MSP 需求
- 文档 §10.3 已提前警告 512B 不够，恢复 W5500/CAN 后果然触发

## 问题九: CAN_User_Init 中断使能顺序错误

**时间段**: 2026-07-24 下午

**症状**:
潜在——CAN 错误 ISR 在信号量尚未创建时触发 → `xSemaphoreGiveFromISR(NULL)` → `configASSERT` → 死循环。

**根因**:
`CAN_User_Init()` 中中断使能和信号量创建顺序反了：

```c
// 错误顺序:
CAN_ITConfig(CAN1, CAN_IT_ERR, ENABLE);   // ← 先使能中断
CAN_NVIC_Init();                             // ← 在 NVIC 层也使能
g_can_monitor_sem = xSemaphoreCreateBinary(); // ← 后创建信号量
```

若 CAN 外设在 init 后立即因总线噪声/ACK 错误触发 `CAN1_SCE_IRQHandler`，此时 `g_can_monitor_sem` 为 NULL，`xSemaphoreGiveFromISR(NULL)` 触发 `configASSERT` → 关中断 + 死循环。

**修复** (CAN_User.c, Master + Slave):
```c
// 正确顺序: 先创建所有内核对象
g_can_rx_sem         = xSemaphoreCreateBinary();
g_can_fifo_not_empty = xSemaphoreCreateBinary();
g_can_monitor_sem    = xSemaphoreCreateBinary();
FIFO_Init();             // 创建 mutex

// 再使能中断
CAN_ITConfig(CAN1, CAN_IT_FMP0, ENABLE);
CAN_ITConfig(CAN1, CAN_IT_ERR, ENABLE);
CAN_ITConfig(CAN1, CAN_IT_BOF, ENABLE);
CAN_NVIC_Init();
```

**涉及文件**:
- `CanEdgeGateWay_Master/Hardware/CAN_User.c`
- `CanEdgeGateWay_Slave/Hardware/CAN_User.c`

## 问题十: Task_W5500 临界区阻塞 SysTick → 任务饿死

**时间段**: 2026-07-24 下午

**症状**:
`Task_W5500` 用 `taskENTER_CRITICAL()` 包裹 `W5500_TCPServer_Run()`，导致 SysTick 中断被屏蔽，Tick 计数不增长，其他任务因 `vTaskDelayUntil` 无法到期而饿死。IWDG 在 1 秒后复位系统。

**根因**:
- `taskENTER_CRITICAL()` 设置 `BASEPRI = 0x50`
- SysTick 优先级 15，NVIC 寄存器值 `0xF0`，满足 `0xF0 ≥ 0x50` → **被屏蔽**
- 同时 PendSV（优先级 15 = `0xF0`）也被屏蔽 → 无法上下文切换
- `W5500_TCPServer_Run` 内部 `SocketCmd` 超时循环用 `Delay_us(DWT)` 消耗真实时间（200ms/次），但不产生任何 Tick
- 退出临界区后 Tick 追赶式增长，但 Housekeep 的 `vTaskDelayUntil(1000ms)` 实际上隔了数秒才到期
- 期间 IWDG 已超时复位

**修复**：
W5500 独占 SPI1（OLED 是软件 I2C，CAN 是 bxCAN），无需临界区保护。移除 `taskENTER_CRITICAL/taskEXIT_CRITICAL`：

```c
for (;;) {
    W5500_TCPServer_Run();    // 无临界区
    ModbusTCP_Process();      // 无临界区
    vTaskDelay(pdMS_TO_TICKS(5));
}
```

**涉及文件**:
- `CanEdgeGateWay_Master/User/main.c`

**经验**:
- BASEPRI 不是 PRIMASK！`taskENTER_CRITICAL()` 只屏蔽优先级 ≥ 阈值的中断。SysTick 和 PendSV 通常设为最低优先级（15），恰好被 BASEPRI 挡住。
- 一个任务在临界区里吃 DWT 延时 = 整个系统停摆（比 `vTaskDelay` 更恶劣，因为 Tick 不前进）。
- 临界区的正确使用场景：多个任务共享同一外设（如 SPI Flash）。单任务独占的外设不需要临界区。

## 问题十二: CAN_ProcessFrame 在任务上下文调用 xSemaphoreGiveFromISR

**时间段**: 2026-07-24 傍晚（阶段二-2 深度排查）

**症状**:
调度器启动后系统卡 "M: Starting..."，无 HardFault、无 STACK OVERFLOW 提示。所有 init 通过，xTaskCreate 全部成功，但调度器启动后立即挂死。

**根因**:
`CAN_ProcessFrame()` 由 `Task_CAN_Rx`（任务上下文，prio 5）调用，但内部使用了 `xSemaphoreGiveFromISR()`：

```c
// CAN_User.c — CAN_ProcessFrame (called from Task_CAN_Rx)
static BaseType_t tx_woken = pdFALSE;
xSemaphoreGiveFromISR(g_can_fifo_not_empty, &tx_woken);  // ← 致命错误
xSemaphoreGive(g_can_fifo_not_empty);                     // ← 还重复给了两次
```

`xSemaphoreGiveFromISR` 内部调用 `xQueueGiveFromISR`，该函数会:
1. 调用 `xTaskRemoveFromEventList()` — 操作调度器的 `xPendingReadyList`
2. 修改就绪优先级位图 `uxReadyPriorities`
3. 这些操作必须与 `xTaskIncrementTick()`（在 SysTick 中运行）互斥

在 ISR 上下文中，互斥由中断优先级保证（BASEPRI 挡不住优先级 0-4 的 ISR，但 FromISR 函数内部有 `portASSERT_IF_INTERRUPT_PRIORITY_INVALID` 检查——前提是 `configASSERT_DEFINED=1`）。

在任务上下文中**没有任何保护**——`xTaskRemoveFromEventList` 和 `xTaskIncrementTick` 同时修改同一组链表，造成**链表指针损坏**。

损坏后的就绪列表在下一次 PendSV 上下文切换时遍历到野指针 → 系统挂死在 `vTaskSwitchContext` 中。

**为什么调试版不触发**：调试版没有创建 `Task_CAN_Rx`（`#if 0` 包裹），`CAN_ProcessFrame` 从未被调用。

**修复** (CAN_User.c):
```c
// 删除:
static BaseType_t tx_woken = pdFALSE;
xSemaphoreGiveFromISR(g_can_fifo_not_empty, &tx_woken);
xSemaphoreGive(g_can_fifo_not_empty);

// 替换为:
xSemaphoreGive(g_can_fifo_not_empty);
```

## 问题十三: 多任务抢占 SPI 总线（无声数据竞争）

**时间段**: 2026-07-24 傍晚

**症状**:
`ETH_StateStr()`（由 `Task_Housekeep` prio 0 调用）直接调 `W5500_LinkUp()` = `R_Common(REG_PHYCFGR)` = SPI 读。当 `Task_W5500`（prio 1）在 SPI 操作中被 SysTick 打断后恢复时，Housekeep 可能正好在中间操作 SPI1 寄存器。

**根因**:
两个不同优先级的任务通过不同代码路径共享 SPI1：

| 任务 | 优先级 | 如何访问 SPI |
|------|--------|-------------|
| `Task_W5500` | 1 | 主循环 `W5500_TCPServer_Run()` |
| `Task_Housekeep` | 0 | `OLED_UpdateDisplay()` → `ETH_StateStr()` → `W5500_LinkUp()` |

SPI1 外设只有一组寄存器。两个任务在不同优先级上操作同一组寄存器，任何交叉访问都会破坏对方的传输。

**为什么临界区不能解决这个问题？** 因为 `taskENTER_CRITICAL` 会锁死 SysTick（§15）。正确的做法是用互斥锁或将 SPI 访问集中于一个任务。

**修复** (W5500.h/c, main.c):
W5500 任务将 `g_phy_linked`（PHY 链接状态）每 5ms 缓存一次。其他任务通过 `W5500_IsLinkUpCached()` 读取缓存，不触 SPI：

```c
// W5500.c — 在 W5500_TCPServer_Run 中更新
g_phy_linked = W5500_LinkUp();   // SPI 操作只在 W5500 任务中

// W5500.h — 对外暴露无 SPI 的缓存读取
uint8_t W5500_IsLinkUpCached(void) { return g_phy_linked; }

// main.c — OLED 用缓存
if (!W5500_IsLinkUpCached()) return "NOLK";
```

**涉及文件**:
- `CanEdgeGateWay_Master/Hardware/W5500.h`
- `CanEdgeGateWay_Master/Hardware/W5500.c`
- `CanEdgeGateWay_Master/User/main.c`

## 问题十四: 调度器启动前 ISR 已置位信号量

**时间段**: 2026-07-24 傍晚

**症状**:
CAN 错误 ISR 在 `vTaskStartScheduler()` 之前触发，将 `g_can_monitor_sem` 置位。调度器启动后 PendSV 立即切换到 `Task_CAN_Monitor`（prio 4），在 Idle 任务上下文尚未完全建立时运行——虽然不会立即崩溃，但可能干扰优先级就绪队列的初始状态。

**根因**:
`CAN_User_Init` 在 `main()` 中被调用，ISR 在 `vTaskStartScheduler()` 之前即可触发。即使信号量在 ISR 之前已创建（问题九已修复），ISR 的 Give 操作会将信号量置位。调度器启动时，等待该信号量的任务立即就绪。

**修复** (main.c):
在 `vTaskStartScheduler()` 之前 Drain 所有信号量：
```c
{
    BaseType_t sem;
    do { sem = xSemaphoreTake(g_can_monitor_sem, 0); } while (sem == pdPASS);
    do { sem = xSemaphoreTake(g_can_rx_sem, 0); } while (sem == pdPASS);
    do { sem = xSemaphoreTake(g_can_fifo_not_empty, 0); } while (sem == pdPASS);
}
```

**涉及文件**:
- `CanEdgeGateWay_Master/User/main.c`

**核心教训**:
1. MSP 栈溢出无 HardFault——它踩的是堆，不是栈边界
2. BASEPRI 临界区 ≠ 关所有中断——SysTick 和 PendSV 恰好被 BASEPRI 挡在外面
3. 中断使能前必须确保所有 ISR 使用的内核对象已创建——否则 NULL 触发 assert
4. ARMCC 的 `sprintf` 栈消耗极大——256 words 不够，至少 384 words
5. **`xSemaphoreGiveFromISR` 的名字就是字面意思——只能在 ISR 上下文用。在任务上下文调用它会破坏调度器链表，造成看似完全无关的挂死**
6. **SPI 外设应当只有一个"所有者"任务。其他任务需要状态时，通过缓存读取，不直接操作 SPI**
7. **调度器启动前的 ISR 可能已置位信号量。启动前 Drain 一次是安全的防御性编程**
8. 渐进式验证的价值：3 调试任务 → 6 真实任务过程中暴露了 7 个独立运行期问题
